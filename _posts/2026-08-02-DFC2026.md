## 101 - Ghost in the Shell

### 목표와 증거

제공된 증거는 `PowerShell-Operational.evtx`와 `Sysmon-Operational.evtx`이다. 분석은 이벤트 로그에서 문자열을 추출해 **정적으로** 디코딩하는 방식으로 수행했다.

### 타임라인 (KST, UTC+09:00)

| 시각 | 증거 | 의미 |
|---|---|---|
| 13:41:52.175 | Sysmon EID 1, Record 110 | `cmd.exe`에서 `powershell.exe`(PID 5140)가 `-nop -w hidden -ep bypass -enc` 옵션으로 시작됨 |
| 13:41:53.626 | PowerShell EID 4104, Record 121 | `HKCU:\Software\OneDrive\Update` 생성, `DeviceId` 기록, GZip/Base64 2단계 로더 실행 |
| 13:41:53.966 | Sysmon EID 13, Record 113 | `DeviceId` 레지스트리 값 기록 확인 |
| 13:41:54.268 | PowerShell EID 4104, Record 126 | `SyncState` 기록 및 다음 단계 디코딩 |
| 13:41:54.270 / 13:41:54.293 | Sysmon EID 13, Records 114/115 | `SyncState`, `TelemetryCache` 값 기록 확인 |
| 13:41:54.292 | PowerShell EID 4104, Record 130 | 두 값을 결합해 Base64 디코딩 후 XOR 하는 최종 단계 |
| 13:41:55.362 | Sysmon EID 22, Record 120 | `cdn-sync-update.com` DNS 질의. C2/telemetry 용도로 보임 |
| 13:41:55.945 | Sysmon EID 5, Record 116 | PID 5140 종료 |

### 난독화 구조

초기 명령줄은 Base64 인코딩된 PowerShell이며, 창 숨김과 실행 정책 우회를 사용한다. Script Block Logging(EID 4104)에는 이미 복호화된 스크립트가 기록되어 있어 실제 실행 없이 로직을 파악할 수 있다.

1. 1단계와 2단계는 `$b`에 Base64 문자열을 저장한다.
2. `[Convert]::FromBase64String`과 `IO.Compression.GzipStream`으로 다음 스테이지를 복원한 뒤 `IEX` 하도록 작성되어 있다.
3. 레지스트리의 `DeviceId`는 XOR 반복키, `SyncState`와 `TelemetryCache`는 암호문 두 조각이다.
4. 최종 스테이지는 두 조각을 정확히 `SyncState + TelemetryCache` 순서로 붙인 뒤 Base64 디코딩하고, 반복키로 XOR한다.

### 재현 절차

1. EID 4104 및 Sysmon EID 1, 5, 12, 13, 22를 시간순으로 내보낸다.
2. PID `5140` 및 ProcessGuid `{c2b4f1c1-6010-6a3b-4202-000000000300}`로 이벤트를 상관 분석한다.
3. 4104 Record 121/126의 `$b` 문자열을 Base64 디코딩한 후 GZip 해제한다. `IEX`는 절대 실행하지 않는다.
4. 아래 값이 4104와 Sysmon EID 13(Records 113~115)에서 동일한지 확인한다.

```powershell
$device='UjNkVDM0bV9ERkM='
$sync='FH8lE0hQXm8mIDYhUFAgAG'
$tele='sVbzYZIGJBFmdfABlsOQ=='
```

5. `DeviceId`를 Base64 디코딩하면 XOR 키 `R3dT34m_DFC`가 나온다.
6. `SyncState + TelemetryCache`를 Base64 디코딩하고, 바이트 `i`마다 `key[i % key.length]`를 XOR한다.

```powershell
$k=[Convert]::FromBase64String($device)
$ct=[Convert]::FromBase64String($sync+$tele)
$flag=-join (0..($ct.Length-1) | % { [char]($ct[$_] -bxor $k[$_ % $k.Length]) })
$flag
```

출력 평문 바이트는 `46 4C 41 47 7B 64 33 30 62 66 75 73 63 34 74 33 5F 78 30 72 5F 63 30 72 72 33 6C 34 74 33 7D`이다.

### 사용 도구
- PowerShell: `Get-FileHash`, `Get-WinEvent`, Base64/XOR 확인
- .NET: `Convert`, `GzipStream`
- 정적 텍스트/이벤트 로그 분석

## 151 - Pull the Plug?

### 결론

복호화는 가능하다. 분석 시점에 LUKS 볼륨 `vault`가 활성화되어 있었고, 디스크에만 존재하는 LUKS 헤더 정보뿐 아니라 dm-crypt가 사용 중인 AES 키 스케줄이 1 GiB 저장 메모리에 남아 있었다. 즉 비밀번호를 추측하거나 크랙하지 않고, 메모리에서 복원한 volume key를 LUKS 헤더의 digest로 검증해 읽기 전용으로 열 수 있다.

### 증거 식별 및 상태 판정

VMDK의 논리 디스크를 읽어 ext4 루트 파티션(LBA `4462592`)을 분석하면 `/root/vault.img`(33,554,432 bytes)를 얻을 수 있다. 메모리에는 다음 활성 상태 증거가 있다.
- `cryptsetup open /root/vault.img vault`
- dm-crypt mapping `vault`
- LUKS UUID `73bc4374-a2e1-47da-8e2a-5df2af3905f3`

`cryptsetup luksDump vault.img`의 핵심 정보는 다음과 같다.

| 항목 | 값 |
|---|---|
| LUKS 버전 | LUKS2 |
| Cipher | `aes-xts-plain64` |
| Volume key | 512 bit |
| Sector size | 4096 bytes |
| Payload offset | 16,777,216 bytes |
| Keyslot KDF | Argon2id |
| Digest | PBKDF2-HMAC-SHA256, 258015 iterations |

### 메모리 키 복구 방식

AES-XTS 512 bit key는 AES-256 키 두 개(각 32 bytes)로 구성된다. Linux의 AES 구현은 키를 확장한 AES-256 round-key schedule을 메모리에 보관한다. 따라서 메모리를 AES-256 key schedule 규칙으로 스캔해 후보 원키를 얻을 수 있다.

1. 16-byte 정렬 영역을 기준으로 메모리를 스캔한다.
2. AES-256 key expansion의 `SubWord`, `RotWord`, `Rcon` 관계를 만족하는 240-byte schedule을 찾는다.
3. 각 schedule에서 원래 32-byte 키를 역으로 얻는다.
4. 후보 두 개를 순서대로 이어 64-byte volume key를 구성한다.
5. LUKS header의 PBKDF2 digest와 비교한다. digest가 일치하는 후보만 진짜 volume key다.

이 검증으로 오탐 schedule 및 흔한 AES test vector를 제외할 수 있다. 복호화 key 자체는 산출물에 기록하지 않고 임시 보호 파일에서만 사용했다.

### 재현 절차

1. ZIP 해시를 검증한 뒤 VM을 부팅하지 않고 별도 증거 디렉터리에 압축을 푼다.
2. `pyvmdk`/libvmdk로 monolithic sparse VMDK를 논리적으로 읽는다.
3. `pytsk3`로 root ext4 파티션을 열고 `/root/vault.img`를 추출한다.
4. `cryptsetup luksDump`로 cipher, key size, payload offset, PBKDF2 salt/digest를 기록한다.
5. `.vmem`을 AES-256 expanded-key schedule로 스캔한다.
6. 후보 half-key 조합의 `PBKDF2-HMAC-SHA256(volume_key, luks_digest_salt, 258015)`가 LUKS digest와 같은지 확인한다.
7. 검증된 key file로만 읽기 전용 mapping을 연다.

```bash
cryptsetup open --readonly --master-key-file <verified-key-file> vault.img vault
mount -o ro /dev/mapper/vault /mnt/vault
cat /mnt/vault/flag.txt
cryptsetup close vault
```

8. `/mnt/vault/flag.txt`에서 플래그를 확인한다. 분석 종료 후 mapping과 임시 key file을 제거한다.

### 사용 도구
- `pyvmdk` / libvmdk: sparse VMDK 논리 읽기
- `pytsk3`: ext4 파일시스템 분석 및 `vault.img` 추출
- Python: AES-256 key schedule 탐지 및 PBKDF2 digest 검증
- `cryptsetup`: LUKS2 metadata 확인 및 읽기 전용 mapping

## 152 - MnemonicYum_Link

### 주소 파생

제시 문구는 유효한 BIP39 12-word mnemonic이다. TRON의 일반 BIP44 경로를 적용한다.

```text
m/44'/195'/0'/0/0
```

절차는 다음과 같다.
1. BIP39 mnemonic에서 seed를 생성한다.
2. BIP44 purpose `44'`, TRON coin type `195'`, account `0'`, external chain `0`, address index `0`을 차례대로 파생한다.
3. 파생된 공개키 hash에 TRON network prefix `0x41`을 붙인다.
4. SHA-256 이중 해시의 앞 4 bytes checksum을 붙여 Base58Check로 인코딩한다.

`bip-utils`로 계산한 결과가 `TPChqavCK3e4S6UCGGUCKnt6yeKn1XbugL`이다. 개인키는 분석 결과물에 기록하거나 전송하지 않는다.

### 온체인 분석 (Nile)

Nile TronGrid API로 해당 주소의 확정 트랜잭션과 TRC20 기록을 조회했다.

| 관찰 | 내용 |
|---|---|
| USDT 유입 | `1,000.000000 USDT` 및 `1,944.180966 USDT` 유입 기록 |
| 권한 변경 | `e663de6fde24a64faf1548eae943bfe1933ea27d4239d8617064e64643fe62c8`가 `AccountPermissionUpdateContract` 실행 |
| threshold | owner 및 active permission 모두 `3` |
| 피해 주소 키 weight | `1` |
| `TEqVC...` 키 weight | `2` |
| 후속 흐름 | 권한 변경 뒤 `TEqVC...`로 반복적인 TRX 출금 발생 |

권한 업데이트에는 피해 키 외에 `TEqVC...`(weight 2)와 추가 키 두 개(weight 1씩)가 들어 있다. threshold가 3이므로 mnemonic에서 얻은 피해 키(weight 1)만으로는 owner/active 권한을 충족하지 못한다. 반면 `TEqVC...`는 다른 보조 키 하나와 조합해 출금 권한을 충족할 수 있다.

### 재현 절차

1. ZIP hash를 검증하고 `post.txt`에서 mnemonic을 얻는다.
2. BIP39/BIP44 라이브러리로 `m/44'/195'/0'/0/0`을 파생한다.
3. 아래 Nile API를 조회한다.

```text
https://nile.trongrid.io/v1/accounts/TPChqavCK3e4S6UCGGUCKnt6yeKn1XbugL/transactions/trc20?only_confirmed=true&limit=200
https://nile.trongrid.io/v1/accounts/TPChqavCK3e4S6UCGGUCKnt6yeKn1XbugL/transactions?only_confirmed=true&limit=200
```

4. TRC20 endpoint에서 USDT 유입을 확인한다.
5. 일반 transaction endpoint에서 `AccountPermissionUpdateContract`를 찾아 threshold, 키 주소, 각 weight를 기록한다.
6. 21-byte hex TRON 주소(`41` prefix 포함)를 Base58Check로 변환해 권한 키를 사람이 읽을 수 있는 TRON 주소로 비교한다.
7. 권한 변경 시점 이후 outgoing transfers의 수신자가 `TEqVCMiYoHs5H7fhqC7zqgWuXkeZWKKDBc`인지 확인한다.

### 사용 도구
- Python 및 `bip-utils`: BIP39 seed, BIP44 TRON address derivation
- SHA-256 / Base58Check: TRON address encoding 검증
- Nile TronGrid REST API: 확정 TRC20/일반 transaction과 account permission 분석
- Pillow 및 `rg`: PNG 메타데이터/내장 문자열 점검
