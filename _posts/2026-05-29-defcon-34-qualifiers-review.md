## TJCTF 1위, 그리고 바로 이어진 DEF CON 예선

TJCTF 2026에서 처음 합을 맞춘 뒤, 같은 팀원들과 **DEF CON CTF Qualifier 2026**에 참가했다. 대회는 5월 23일부터 25일까지 온라인 Jeopardy 형식으로 진행됐다. TJCTF에서는 팀원들의 풀이를 따라가며 배우는 쪽에 가까웠지만, 이번에는 리버싱 한 문제와 misc 한 문제에 직접 손을 보탤 수 있었다.

![DEF CON CTF Qualifier 2026 대회 정보](/assets/img/defcon-34-qualifiers/event-info.png)
_2026년 5월 23일부터 25일까지 열린 DEF CON CTF 예선._

최종 결과는 **673개 팀 중 6위**였다. Jinddabi's라는 이름으로 본선 진출권을 얻었고, 이후 DEF CON 34 Finals에 참가하게 됐다. TJCTF에서 팀의 속도에 놀라기만 했던 때와 달리, 이번에는 작더라도 내가 분석한 내용을 팀 채널에 남기고 다음 판단의 근거로 연결했다는 점에서 의미가 컸다.

![DEF CON CTF Qualifier 2026 최종 스코어보드](/assets/img/defcon-34-qualifiers/scoreboard.png)
_Jinddabi's는 8,844점을 기록하며 전체 6위로 예선을 마쳤다._

이 글에 정리한 두 문제의 분석과 풀이 과정은 모두 내가 직접 진행한 내용이다. 다만 플래그와 완성 exploit을 그대로 공개하는 상세 라이트업보다는, 어떤 가설을 세우고 어떻게 분석 방향을 좁혀 갔는지를 기록한 참가 후기에 가깝다.

## 1. 2bird2can: 배를 직접 움직이는 것만이 답은 아니었다

`2bird2can`은 바다 위의 배를 조종해 숨겨진 보물 상자를 찾아 상호작용하는 리버싱 문제였다. 대상은 **Unity IL2CPP 기반의 헤드리스 Linux 서버 빌드**였고, 브라우저 화면 뒤에서는 바이너리 형태의 실시간 통신이 오갔다.

![2bird2can 분석을 시작한 팀 채널 기록](/assets/img/defcon-34-qualifiers/2bird2can-channel.png)
_원격 환경만 바라보지 않고 로컬 실행 환경부터 재현했다._

### 먼저 로컬에서 통제권을 확보하기

원격 서버가 불안정한 상황에서 무작정 접속을 반복하기보다 Docker Compose로 서버를 로컬에 올렸다. 서버 로그에서는 월드 seed, 보물 상자가 생성된 청크와 인게임 좌표를 확인할 수 있었다. 별도의 HTTP 지도 엔드포인트도 발견했고, 지도 중앙 부근의 X 표시와 실제 좌표 사이의 관계를 비교했다.

여기까지는 “보물이 어디에 있는가”를 알아내는 단계였다. 하지만 좌표를 안다고 해서 거대한 맵을 정상 속도로 이동할 수 있는 것은 아니었다. 결국 다음 질문은 **어떻게 그 위치에 도달하거나, 멀리서도 상호작용할 것인가**였다.

### 실패한 WebSocket 변조

처음에는 배의 이동 패킷을 조작하는 방법을 시도했다. 그러나 WebSocket 메시지는 JSON이 아니라 수십 바이트 길이의 이진 데이터였고, 단순히 좌표 문자열을 바꿀 수 있는 구조가 아니었다. 브라우저에서 WebSocket 생성자를 후킹하는 방법도 시험했지만 Unity Netcode의 연결 과정과 맞지 않아 서버가 세션을 끊었다.

이 실패로 프론트엔드에서 통신만 가로채는 접근의 한계가 분명해졌다. 그래서 `GameAssembly.so`와 IL2CPP 메타데이터를 기준으로 실제 게임 로직을 확인하는 방향으로 전환했다.

### 이동 속도가 아니라 상호작용 범위를 본 이유

처음 떠오르는 방식은 이동 입력을 크게 만들어 배를 빠르게 보내는 것이었다. 하지만 이 방법은 패킷 구조와 서버 검증을 함께 풀어야 했다. 대신 나는 문제를 “배를 보물까지 보낸다”가 아니라 **보물이 현재 배의 상호작용 범위 안에 들어오게 만든다**로 바꿔 보았다.

즉 배의 scale, 충돌 판정 크기, 상호작용 반지름처럼 클라이언트 또는 게임 로직이 신뢰하는 값을 크게 만들 수 있는지 찾는 방향이었다. 설정 파일이 따로 보이지 않았기 때문에 관련 값이 바이너리에 하드코딩됐을 가능성을 두고 분석 범위를 좁혔다. 속도 핵처럼 통신 자체를 완전히 해석하는 대신, 게임의 판정 로직을 리버싱해 우회 지점을 찾는 관점이었다.

이 문제에서 가장 크게 배운 것은 목적과 수단을 분리하는 일이었다. 보물에 도달하는 것이 목적이라면 반드시 배를 정상적으로 항해시킬 필요는 없다. 한 접근이 복잡해질 때 같은 성공 조건을 만족시키는 다른 변수를 찾는 것이 리버싱에서도 중요했다.

## 2. rfc1149a: 찢어진 패킷을 다시 한 흐름으로

`rfc1149a`는 바이트 일부가 훼손된 **44개의 TCP/IP 패킷 조각**을 정렬하고, 그 안에서 유효한 HTTP/Gzip 데이터 스트림을 복구하는 misc 문제였다. 처음 파일들을 보았을 때는 헤더도 군데군데 망가져 있었고 데이터·ACK·재전송·정적 파일 요청이 한데 섞여 있어 무엇부터 이어야 할지 막막했다.

![rfc1149a에서 패킷 위치를 나눠 맡은 기록](/assets/img/defcon-34-qualifiers/rfc1149a-roles.png)
_패킷 번호별로 구간을 나누고 각자 확인한 바이트를 공유했다._

### 눈으로 맞추기 전에 흐름을 나누기

각 프레임에서 IP ID, 출발지·목적지 포트, TCP Sequence와 Acknowledgment 번호를 뽑아 표처럼 정리했다. 보이지 않거나 의심스러운 바이트는 HTTP 형식과 체크섬을 이용해 후보를 검산했다. 이 과정을 거치자 44개 파일이 하나의 긴 데이터가 아니라, 서로 다른 포트를 사용하는 몇 개의 TCP 흐름과 제어 패킷으로 나뉘기 시작했다.

![손상된 패킷의 바이트를 비교하며 공유한 기록](/assets/img/defcon-34-qualifiers/rfc1149a-bytes-1.png)
_가려진 헤더 바이트를 위치별로 정리하고 가능한 값을 좁혔다._

![다른 구간의 패킷 바이트를 이어 맞춘 기록](/assets/img/defcon-34-qualifiers/rfc1149a-bytes-2.png)
_Sequence·ACK와 주변 바이트가 서로 모순되지 않는지 계속 교차 확인했다._

### 시작점과 끝점을 찾는 기준

데이터 패킷에서는 HTTP 응답 헤더, Gzip 매직 바이트, chunked encoding의 종료 표식이 좋은 이정표가 됐다. 같은 포트와 이어지는 Sequence 번호를 가진 조각을 묶고, 시작 헤더가 있는 패킷부터 종료 chunk까지 연결했다. 반대로 페이로드가 없는 순수 ACK나 FIN은 데이터가 아니라 흐름의 경계를 검산하는 데 사용했다.

또한 Sequence 번호와 내용이 완전히 같은 조각은 재전송으로 판단해 한 번만 사용했다. `style.css`나 테마 CSS처럼 정상적으로 복원되지만 플래그와 무관한 정적 리소스도 별도 흐름으로 격리했다. 무엇이 중요한지 찾는 일만큼, **그럴듯하지만 무관한 데이터를 버리는 일**도 중요했다.

### 웹 취약점에서 패킷 복원으로 돌아오기

중간에는 프록시 헤더 주입, URI 정규화 차이, 신뢰 IP 위조, HTTP 메소드 변경 같은 웹 우회도 시험했다. 하지만 모두 막혔고, 문제의 핵심은 서버를 속이는 데 있지 않았다. 다시 패킷으로 돌아와 훼손된 헤더를 보정하고 TCP 흐름과 압축 데이터를 복원하는 데 집중했다.

![rfc1149a의 웹 우회 가능성을 논의한 기록](/assets/img/defcon-34-qualifiers/rfc1149a-web.png)
_웹 취약점 가능성도 확인했지만, 실패를 확인한 뒤 패킷 재조립에 집중했다._

이 문제는 화려한 한 번의 트릭보다 지루해 보이는 검산이 답에 가까웠다. 포트, Sequence, ACK, 길이, 체크섬을 한 항목씩 맞추면 손상된 조각 사이에도 순서가 생겼고, 끝내 완결된 Gzip 스트림을 복구할 수 있었다.

## 예선에서 처음 느낀 ‘내 몫’

TJCTF 후기에서는 내가 거의 도움을 주지 못했다고 적었다. 불과 며칠 뒤 치른 DEF CON 예선에서도 팀원들의 속도와 실력은 여전히 놀라웠지만, 이번에는 상황이 조금 달랐다. `2bird2can`에서는 로컬 서버를 재현하고 좌표와 통신 구조를 확인한 뒤 공격 관점을 바꿨고, `rfc1149a`에서는 손상된 패킷을 분류하고 흐름을 복원하는 작업을 직접 맡았다.

풀이 과정은 팀 채널에서 “이 패킷은 어느 흐름인가”, “이 접근은 왜 실패했는가”, “다음에는 무엇을 확인할 것인가”를 계속 공유하며 진행했다. 내가 직접 분석한 중간 결과를 즉시 팀에 전달하고, 대화에서 얻은 피드백을 다시 다음 분석의 출발점으로 삼는 경험이 온라인 팀 CTF의 재미였다.

최종 6위와 본선 진출은 팀 전체가 만든 결과다. 그 안에서 이번에는 분명 내가 직접 붙잡고 분석한 두 문제가 있었다. TJCTF가 팀의 높은 수준을 처음 체감한 대회였다면, DEF CON 예선은 그 속에서 나도 맡을 수 있는 역할을 처음 확인한 대회로 기억에 남을 것 같다.
