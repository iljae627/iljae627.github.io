## 시작하며

이번 **DEF CON 34 Finals**에서는 팀원들과 함께 KOTH(King of the Hill) 문제인 **BBBQ**를 집중적으로 공략했다. 일반적인 CTF 문제는 정답을 한 번 맞히면 끝나지만, KOTH는 정답을 맞힌 순간부터가 시작이었다. 정상 동작하는 파일을 제출한 뒤에도 다른 팀보다 점수를 조금이라도 더 낮추기 위해 같은 로직을 계속 뜯어고쳐야 했다.

대회 내내 가장 많이 본 것은 플래그가 아니라 아래와 같은 숫자들이었다.

- 실행 명령 수(`insn_count`)
- 큐의 High Water Mark(`HWM`)
- HWM 순간의 큐 불균형(`covariance`)
- 제출 바이트코드의 크기

처음에는 단순히 “정렬을 빠르게 만들면 되는 문제”라고 생각했다. 그러나 문제는 여러 차례 바뀌었고, 그때마다 입력 형식과 정답 조건부터 다시 역추적해야 했다. 결국 이번 대회는 알고리즘 대회이면서 동시에 VM 리버싱, 컴파일러 최적화, 실험 자동화, 그리고 팀 협업을 모두 요구하는 긴 프로젝트가 되었다.

이 글은 완성된 해법을 그대로 공개하는 라이트업이라기보다, 대회 중 어떤 판단을 했고 무엇을 실패했으며 그 과정에서 무엇을 배웠는지를 기록한 참가 후기이다.

## BBBQ와 점수식

제출 파일은 텍스트 코드가 아니라 **little-endian u32 명령어 배열**로 이루어진 `.bbbq` 바이트코드였다. Python으로 작성된 `benchmark.py`는 실행을 도와주는 래퍼에 가까웠고, 실제 명령을 해석하고 점수를 계산하는 것은 별도로 제공된 stripped Linux ELF 실행기였다.

대회에서 사용한 대표적인 점수식은 다음과 같았다.

$$
\text{score}
= \text{HWM} \times (1 + \text{covariance})
+ \ln(\text{insn\_count})
+ \frac{\text{file\_size}}{25000}
$$

점수는 낮을수록 좋았다. 이 식은 네 가지 지표가 서로 다른 방식으로 충돌하게 만들었다.

| 최적화 대상 | 장점 | 함께 생기는 문제 |
|---|---|---|
| HWM 감소 | 한 번 성공하면 점수가 크게 내려감 | 상태를 둘 공간이 줄어 로직이 복잡해짐 |
| covariance 감소 | 같은 HWM에서도 즉시 점수 이득 | 피크 순간의 네 큐 배치를 정확히 통제해야 함 |
| 실행 명령 감소 | 모든 시드에서 안정적인 개선 | 루프 전개 시 파일 크기가 폭증함 |
| 파일 크기 감소 | 바이트 단위로 점수가 직접 감소 | 공유 루프와 분기가 늘어 실행 명령이 증가할 수 있음 |

그래서 단순히 “더 빠른 알고리즘”만 찾는 것으로는 부족했다. 특정 명령 하나의 위치를 바꾸는 일이 HWM을 바꿀 수 있었고, 반대로 수천 바이트를 줄여도 실행 경로가 한 번 더 순환하면 점수가 오를 수 있었다.

## 첫 번째 단계: 정렬 VM을 이해하기

초기 문제에서는 입력된 정수들을 정렬하는 바이트코드를 최적화했다. 처음 팀의 평균 점수는 142점대였고, 루프 전개와 Selection Sort 계열 접근을 이용해 점수를 낮추고 있었다. 이후 팀원이 만든 파일이 129점대에 도달하면서 방향이 크게 바뀌었다.

### Python 래퍼가 아니라 ELF를 봐야 했다

처음에는 `benchmark.py`를 분석하면 VM 규칙이 모두 나올 것이라고 생각했다. 하지만 실제 VM은 `bbbq` ELF 내부에 있었다. 여기서부터 작업은 일반적인 알고리즘 튜닝이 아니라 리버싱 문제가 되었다.

1. `.bbbq` 파일을 4바이트 단위로 분해했다.
2. 상위 비트를 opcode와 queue 번호로 가정하고 분포를 비교했다.
3. ELF의 dispatch 구조와 각 handler를 정적 분석했다.
4. GDB에서 `QPUSH`, `QPOP`, 분기 명령이 실행되는 지점을 추적했다.
5. 두 후보 파일의 바이트 차이를 단순 diff가 아닌 제어 흐름 변화로 해석했다.

이 과정에서 `QPOP`, `QPUSH`, `STASH`, 직접 분기와 간접 분기 등 주요 명령의 역할을 조금씩 복원했다. 특히 분기 위치가 달라지면 22비트 signed displacement와 코드 포인터를 모두 다시 계산해야 했다. 바이트 몇 개를 눈으로 바꾸는 방식이 아니라, 작은 assembler와 relocator가 필요했다.

### 129점에서 124점대로

팀 파일들을 비교해 보니 큰 개선은 새로운 정렬 알고리즘 하나에서만 나오지 않았다. 자주 실행되는 진입 경로를 fall-through로 바꾸고, 매번 만들던 간접 주소를 이미 정렬된 큐 상태와 함께 전달하는 **continuation threading**이 중요한 역할을 했다.

동적 프로파일에서 더 놀라운 사실도 확인했다. 당시 가장 빠른 후보의 실행 명령 중 약 93%가 `QPOP`과 `QPUSH`였다. 주소 계산 명령 몇 개를 줄이는 미세 최적화에는 분명 의미가 있었지만, 큰 폭의 개선을 위해서는 FIFO 큐를 계속 회전시키는 상태 표현 자체를 바꿔야 했다.

이때 처음으로 “기존 코드를 조금씩 고치는 것”과 “표현 방식을 새로 설계하는 것”의 차이를 제대로 느꼈다. 0.001점을 줄이는 일과 1점을 줄이는 일은 같은 종류의 작업이 아니었다.

## 문제는 한 번만 바뀌지 않았다

이번 KOTH가 특히 힘들었던 이유는 문제 업데이트가 계속되었다는 점이다. 이전 문제에서 완벽했던 제출물도 다음 실행기에서는 바로 오답이 되었다. 팀 채널에 새 실행기가 올라올 때마다 모두가 입력과 검증 조건을 처음부터 다시 분석했다.

### 5,348개의 u64와 네 lane

다음 문제는 5,348개의 64비트 입력을 처리해 네 개의 결과를 만드는 형태였다. 인덱스를 4로 나눈 lane별 누적 상태와 상수 1337을 이용한 후처리가 핵심이었다.

이 단계의 가장 큰 화두는 HWM이었다. 큐에 모든 상태를 두지 않고 accumulator와 VM 내부의 숨은 슬롯을 사용하면 HWM을 크게 줄일 가능성이 있었다. 팀에서는 다음과 같은 아이디어들이 빠르게 오갔다.

- 현재 lane의 상태는 accumulator에 유지한다.
- 나머지 상태만 큐에 둔다.
- carry counter를 하나의 packed 값으로 합친다.
- 종료 시점에만 `DIV`와 `MOD`로 counter를 분해한다.
- 큐 배치를 `[1,1,1,1]`에 가깝게 유지해 covariance를 줄인다.

하지만 VM의 `ADD`와 `ADDI`가 일반적인 64비트 wrap-around가 아니라 `UINT64_MAX`에서 포화된다는 함정이 있었다. 종이 위에서 맞는 carry 식이 실제 VM에서는 정보를 잃었다. 반대로 보수 상태에서 뺄셈을 사용하는 방식은 포화 덧셈을 피할 수 있었다.

이 문제를 통해 ISA의 아주 작은 의미 차이가 전체 수학적 설계를 무너뜨릴 수 있다는 것을 배웠다. “아마 일반적인 덧셈일 것”이라는 가정은 역공학에서 가장 위험한 가정 중 하나였다.

### 3 cycle 안의 quine

그다음 문제는 제한된 cycle 안에 자기 자신의 바이트코드를 출력하는 quine이었다. 이전 문제의 복잡한 산술과 달리 목표는 단순해 보였지만, 자기 자신을 출력해야 하므로 명령과 데이터의 경계가 곧 점수였다.

이 단계에서는 다음 최적화가 중요했다.

- 동일 출력 조각 공유
- fall-through를 이용한 분기 명령 제거
- cycle을 깨지 않는 범위에서 코드와 데이터 재배치
- 끝부분 중복 블록 접기
- 파일 크기 감소와 추가 실행 명령 사이의 손익 계산

팀의 점수는 9점대에서 6점대로 내려갔다. 몇 바이트를 줄이는 일이 실제 순위 차이로 이어졌기 때문에, 평소라면 무시할 명령 하나도 그냥 지나칠 수 없었다.

### 100만 개 u64의 unique 복원

또 다른 업데이트에서는 100만 개의 64비트 입력에서 순서 없는 고유 원소 집합을 복원해야 했다. 검증기는 `missing`, `spurious`, `duplicates`, `errors`, `slack`를 따로 계산했다. 여기에 실행 시간 15초 제한까지 추가되었다.

이때부터 정확성은 단순한 `correct=true` 한 번으로 판단할 수 없었다. 어떤 후보는 빠르고 점수도 낮았지만 랜덤 시드에 따라 `bad input`으로 실패했다. 반대로 조금 느린 후보는 많은 시드에서 안정적으로 통과했다.

주최 측 기준상 랜덤 시드 10개 중 일정 횟수 이상 성공하면 통과할 수 있었지만, 로컬 실험에서는 성공률과 실행 시간을 별도로 기록했다. 598점대 후보가 32개 시드 중 21개만 성공했던 사례도 있었고, 실패 원인이 timeout이 아니라 입력 분포에 따른 즉시 오류라는 점도 확인했다. 점수 하나만 보고 제출하면 안 되는 이유였다.

### 마지막까지 이어진 VM 분석

후반 문제에서는 exponent, 큰 modulus, 네 개의 대형 정수 상태를 입력받아 행렬 연산 결과를 출력하는 구조까지 등장했다. 제공된 것은 여전히 실행기뿐이었기 때문에 입력 큐의 초기 상태와 검증기의 출력 비교 방식을 다시 추적했다.

팀의 정상 동작 파일은 로컬에서 약 234점대를 기록했다. 여기서는 알고리즘을 다시 만드는 대신 먼저 구조적으로 확실한 낭비를 제거했다.

- 다음 명령으로 이동할 뿐인 `JMP +0` 제거
- 4명령으로 조립하던 작은 코드 주소를 1~2명령으로 축소
- 연속된 `STASH; STASH` 항등 연산 제거
- 완전히 동일한 303-word 종료 블록 공유
- 동일한 1,012-word 블록을 한 개의 분기로 접기

그 결과 한 로컬 시드에서 약 **234.488 → 234.247**로 점수를 낮출 수 있었다. HWM과 출력은 그대로였고 파일 크기는 279,616바이트에서 273,684바이트로 줄었다. 아주 큰 혁신은 아니었지만, 실제 명령 의미를 보존하면서 구조 재배치로 얻은 안정적인 개선이었다.

## 실패했던 접근들

잘된 일보다 실패한 일이 훨씬 많았다. 특히 기억에 남는 실패는 큐 회전 구간을 작은 반복문으로 압축했던 시도이다.

팀 파일에는 `QPOP q; QPUSH q`가 수백 번 이어지는 구간이 많았다. 정적으로 보기에는 이를 counter loop 하나로 바꾸면 파일 크기를 크게 줄일 수 있었다. 실제로 279,616바이트 파일을 약 53KB까지 줄인 후보도 만들었다.

하지만 랜덤 시드 검증 결과는 0/3, 모두 `bad input`이었다. 동일 시드에서 원본은 234점대로 정상 통과했으므로 실행기나 시드 문제가 아니었다. 반복문으로 바꾸는 과정에서 accumulator, stash, 플래그 또는 간접분기 상태 중 하나를 정확히 보존하지 못한 것이다.

이 실패를 통해 세 가지 원칙을 세웠다.

1. **파일이 작아졌다는 사실은 개선의 증거가 아니다.**
2. **변환 전후에 출력뿐 아니라 HWM, 큐 상태, 명령 수도 비교해야 한다.**
3. **공격적인 변환보다 의미가 자명한 항등 연산 제거부터 적용해야 한다.**

이후에는 `JMP +0`, 최소 폭 주소 조립, 완전히 동일한 종료 블록처럼 의미를 증명할 수 있는 부분부터 줄였다. 개선 폭은 작아졌지만 후보가 깨지는 빈도도 크게 낮아졌다.

## 검증 파이프라인의 중요성

대회 초반에는 후보를 하나 만들 때마다 명령어를 직접 입력해 실행했다. 파일이 많아지고 문제 버전이 계속 바뀌자 이 방식은 곧 한계에 도달했다. 그래서 다음 기능을 가진 로컬 검증 스크립트를 사용했다.

1. 64자리 랜덤 hex seed 생성
2. WSL에서 해당 레벨의 ELF 실행기 호출
3. 실행당 15초 timeout 적용
4. `success`, `correct`, `halted` 확인
5. HWM, covariance, 명령 수, 파일 크기와 score 기록
6. 같은 seed로 기준 파일과 후보 파일 비교

비교할 때 같은 seed를 사용하는 것은 정말 중요했다. 입력에 따라 명령 수가 달라질 수 있으므로 서로 다른 seed의 점수를 비교하면 작은 개선을 잘못 판단하기 쉬웠다.

```text
seed-prefix       baseline      candidate       delta
----------------  ------------  --------------  --------
ee4193e790a8bd5e    234.488040      234.246895  -0.241145
```

또한 WSL 최초 기동 시간과 실제 VM 실행 시간을 분리해 보아야 했다. 첫 실행만 느린 현상을 알고리즘 문제로 오해할 수 있었기 때문이다. 작은 자동화였지만 대회 후반에는 생성기만큼이나 중요한 도구가 되었다.

## 팀 협업과 AI 활용

이번 대회에서는 팀원이 만든 파일 그 자체가 매우 중요한 연구 자료였다. 생성 스크립트가 공유되지 않은 경우에도 이전 버전과 새 버전의 byte delta, opcode 분포, 분기 위치, 동적 실행 횟수를 비교하면 어떤 최적화가 적용되었는지 상당 부분 역추적할 수 있었다.

팀 채널에서는 누군가가 새 파일을 올리면 다른 사람이 여러 seed로 검증했고, 또 다른 사람은 HWM 배치를 분석했다. 한 명이 숨은 슬롯 아이디어를 던지면 다른 사람이 포화 산술의 함정을 찾고, 다시 누군가가 종료부 수식을 고치는 식이었다. 혼자였다면 한 문제의 ISA를 분석하는 데만 대회가 끝났을 것이다.

AI도 분석과 자동화에 적극적으로 활용했다. 반복적인 opcode 통계, 후보 파일 생성, branch relocation, 테스트 결과 정리에 특히 도움이 되었다. 반면 AI가 그럴듯한 VM 의미를 가정해 잘못된 후보를 만들거나, 이미 팀원이 한 개선을 새로운 아이디어처럼 재현하는 문제도 있었다.

결국 AI에게 가장 필요한 것은 긴 명령이 아니라 **검증 가능한 작은 목표**였다.

- “점수를 낮춰라”보다 “두 파일의 동적 opcode 차이를 계산하라.”
- “HWM을 4로 만들어라”보다 “HWM이 처음 갱신되는 PC와 큐 길이를 기록하라.”
- “파일을 압축하라”보다 “직접 진입점이 없는 동일 블록만 찾아라.”

AI가 분석 속도를 높여 준 것은 사실이지만, 최종 판단은 언제나 실제 실행 결과가 내려야 했다.

## 대표적인 점수 변화

문제 버전과 점수식 세부가 계속 달라졌기 때문에 아래 숫자를 하나의 연속된 순위로 볼 수는 없다. 대회 중 로컬에서 확인한 대표적인 변화만 정리하면 다음과 같다.

| 단계 | 대표적인 변화 | 확인한 점수대 |
|---|---|---:|
| 초기 정렬 | 루프 전개, hot entry, continuation threading | 142 → 129 → 124 |
| u64 lane 누적 | 숨은 상태, packed counter, HWM 균형화 | 19.9 → 19.5 |
| quine | 출력 조각 공유, fall-through, 파일 압축 | 9점대 → 6점대 |
| unique 복원 | transient/HWM 조정, timeout 대응 | 598 → 583 |
| 후반 행렬 연산 | 항등 연산 제거와 중복 블록 공유 | 234.488 → 234.247 |

숫자만 보면 몇 줄에 불과하지만, 0.001점을 줄이기 위해 여러 후보를 만들고 수십 개 seed를 돌린 순간도 많았다. 반대로 문제의 상태 표현을 바꾸어 한 번에 몇 점을 줄인 순간도 있었다. KOTH의 재미는 바로 이 두 종류의 개선이 동시에 필요하다는 데 있었다.

## 마무리하며

이번 DEF CON Finals KOTH는 내가 경험한 문제 중 가장 “끝이 없는” 문제였다. 정상 동작하는 파일을 만들면 더 작은 파일이 필요했고, 파일을 줄이면 실행 명령이 늘었으며, HWM을 낮추면 covariance와 종료 로직이 문제를 일으켰다. 그리고 겨우 균형점을 찾으면 다음 문제 버전이 올라왔다.

그 과정에서 가장 크게 배운 것은 세 가지이다.

첫째, **리버싱은 opcode 이름을 붙이는 것으로 끝나지 않는다.** 실제 입력과 상태 변화, 예외적인 산술 의미까지 동적으로 확인해야 한다.

둘째, **최적화는 측정에서 시작한다.** 가장 비싸 보이는 코드를 고치는 것보다 실제 동적 실행의 90% 이상을 차지하는 부분을 찾는 것이 먼저다.

셋째, **팀이 가진 서로 다른 관점이 가장 강력한 최적화 도구다.** 알고리즘, 수학, 리버싱, 자동화 중 어느 하나만으로는 이번 문제를 끝까지 따라가기 어려웠다.

대회 중에는 점수 0.001에 매달리느라 제대로 느끼지 못했지만, 지나고 보니 하나의 작은 VM을 팀원들과 함께 해부하고, 컴파일러를 만들고, 계속 바뀌는 사양에 대응한 경험 자체가 가장 큰 성과였다. 다음 KOTH에 참여하게 된다면 처음부터 disassembler, assembler, profiler, differential validator를 한 묶음으로 준비하고 싶다.

그리고 그때도 분명 마지막에는 같은 말을 하고 있을 것 같다.

**“조금만 더 줄일 수 있지 않을까?”**
