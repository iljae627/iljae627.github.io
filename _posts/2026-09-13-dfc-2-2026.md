이번 **Digital Forensic Challenge 2026 (DFC 2026)** 2차 챌린지에 팀으로 참가하여 다루었던 문제 중 하나인 **Who Stole My Storage**에 대한 분석 경험과 대회 소회 포스팅입니다[cite: 3].

본 글은 대회 운영 방침과 출제 문제 보안을 준수하기 위해 문제의 직접적인 정답(최종 플래그)이나 세부 튜플 문자열은 일체 포함하지 않습니다. 클라우드 및 컨테이너 인프라 환경에서 어떠한 방식으로 아티팩트를 다루고 접근했는지, 그리고 분석 과정과 대회를 통해 얻은 인사이트 위주로 내용을 한층 더 다채롭게 정리해 보았습니다.

## 📌 1. 문제 배경 및 포렌식적 맥락 (Context)

최근 보안 침해 사고 현장에서는 온프레미스 서버 단독 공격보다 **Kubernetes 기반 컨테이너 클러스터** 및 **MinIO / AWS S3와 같은 객체 스토리지(Object Storage)**를 타깃으로 한 데이터 유출 및 인프라 파괴 공작 사례가 크게 늘고 있습니다[cite: 1, 3].

이번 문제인 *Who Stole My Storage* 역시 이러한 최신 클라우드 침해 사고 시나리오를 충실히 반영하고 있었습니다[cite: 1, 3].

### 시나리오 요구사항 분석
* **제공 아티팩트**: 압축 보관된 스토리지 볼륨 아카이브 (`dfc2026-storage.tar.zst`)[cite: 1, 3]
* **위협 상황**: 미상의 외부 공격자가 객체 스토리지 내 중요 자산(데이터베이스 백업 및 Kubernetes etcd 스냅샷 등)에 불법 접근하여 이를 외부에 다운로드함[cite: 3]. 동시에 자신의 범행 흔적을 은폐하고 시스템 복구를 방해하기 위해 데이터 원본과 감사 로그(Audit Log)를 잇달아 삭제함[cite: 3].
* **분석 과제**: 스토리지 영구 볼륨(PV) 내 수집되어 있던 감사 로그를 바탕으로 무단 데이터 유출 및 파괴 행위를 수행한 외부 공격자의 주체 식별 튜플(Access Key, Source IP, User-Agent) 패턴을 특정하는 것[cite: 1, 3]

## 🔍 2. 단계별 분석 접근법 (Methodology)

### Step 1. 아티팩트 무결성 산출 및 볼륨 구조 탐색
아티팩트 수거 시 기본이 되는 무결성 검증부터 진행했습니다[cite: 1, 3]. 

- **해시 검증**: `md5sum` 및 `sha256sum`을 실행하여 아티팩트가 훼손되지 않았음을 명확히 기록했습니다[cite: 1, 3].
- **Zstandard 압축 해제**: `.zst` 확장자를 해제하여 내부 아카이브(`dfc2026-storage.tar`)를 추출했습니다[cite: 1].
- **안전한 구조 확인**: 아카이브 내부의 디렉터리 경로 오염이나 오버라이드 위험을 방지하기 위해 `tar -tvf` 명령으로 구조를 먼저 파악한 후, Kubernetes 영구 볼륨 데이터인 `audit-sink-pv.tar`와 그 내부의 `live-audit.ndjson` 감사 로그를 차례로 추출해냈습니다[cite: 1, 3].

### Step 2. 대용량 NDJSON 감사 로그 분석 쿼리 설계
추출된 `live-audit.ndjson`은 각 API 요청 이벤트가 라인 단위 JSON으로 기록된 **NDJSON(Newline Delimited JSON)** 형식이었습니다[cite: 1, 3]. 수많은 정상 pod 간의 내부 통신 이벤트 속에서 악의적인 행위만을 정밀 정제하기 위해 다음 3가지 필터링 기준을 설정했습니다[cite: 2, 3]:

1. **응답 성공 건 조건 (`statusCode < 400`)**: 단순 탐색이나 권한 부족(403 Forbidden)으로 실패한 단순 스캔 요청을 제외하고, 실제로 데이터가 탈취되었거나 삭제가 완결된 성공 행위만 걸러냅니다[cite: 2, 3].
2. **핵심 위협 메서드 (`GetObject` / `DeleteObject`)**: 단순 목록 조회(ListBuckets 등)가 아닌 실제 데이터를 다운로드하거나 원본/로그를 지우는 핵심 파괴 작업에 집중합니다[cite: 2, 3].
3. **대외망 IP 구분 (External Traffic)**: 내부 사설 IP 대역(`10.x.x.x`)이나 루프백(`127.0.x.x`)에서 발생하는 정상적인 클러스터 internal 트래픽을 제외하고 외부에서 유입된 IP를 선별합니다[cite: 2, 3].

### Step 3. 커맨드라인 자동화 파이프라인 (`jq`) 구축
설정한 필터링 로직을 반영하여, 로그 전체에서 공격 주체를 유일하게 뽑아낼 수 있는 Bash 및 `jq` 파싱 스크립트를 구성하였습니다[cite: 1, 2, 3].

* **응답 코드 및 API 이름 조건 검증**[cite: 2, 3]
* **외부 IP 문자열 매칭 처리**[cite: 2, 3]
* **`Access Key`, `Source IP`, `User-Agent` 항목 추출 및 정렬 (`sort -u`)**[cite: 2, 3]

이 파이프라인을 통해 수많은 로그 레코드 사이에서 오직 문제의 공격 행위에 해당하는 외부 주체 튜플 1건만을 깨끗하게 추출해낼 수 있었습니다[cite: 1, 3].

## 📊 3. 공격 행위 재구성 및 침입 영향도 평가 (Kill Chain)

식별된 공격 주체의 Access Key와 IP를 기반으로 로그 전체의 관련 이벤트를 다시 조회하여 타임라인을 재구성해 본 결과, 공격자는 클라우드 CLI 관리 도구인 `rclone`을 활용하여 다음과 같은 악의적 행위를 연속적으로 수행했음을 알 수 있었습니다[cite: 3].

1. **DB 백업 데이터 무단 다운로드 (`GetObject`)**: 객체 스토리지에 보관되어 있던 기밀 데이터베이스 백업 파일을 유출했습니다[cite: 3].
2. **원본 DB 백업 삭제 (`DeleteObject`)**: 유출 직후 서비스 차질과 복구 불능을 유도하기 위해 원본 백업 파일을 삭제했습니다[cite: 3].
3. **감사 로그 침해 시도 (`DeleteObject`)**: 추적을 회피하기 위해 MinIO Audit Sink 스토리지 내 실시간 감사 로그 파티션 삭제를 시도했습니다[cite: 3].
4. **K8s 클러스터 인프라 파괴 (`DeleteObject`)**: Kubernetes 클러스터의 상태 정보가 저장되는 etcd 스냅샷 파일까지 삭제하여 전체 인프라 마비를 노렸습니다[cite: 3].

## 💡 4. 대회 참가 소회 & 주요 Takeaways

* **클라우드 네이티브 포렌식 역량의 가치 체감**: 전통적인 파일시스템 포렌식이나 로컬 OS 아티팩트 분석을 넘어, 컨테이너 볼륨과 Cloud/S3 감사 로그 분석이 실제 침해 사고 대응에서 얼마나 막중한 비중을 차지하는지 다시금 깊이 느낄 수 있었습니다[cite: 1, 3].
* **리눅스 CLI 텍스트 파이프라인의 강점**: 대용량 NDJSON 로그를 파싱할 때 GUI 기반 도구에만 의존하기보다, `jq`, `grep`, `awk` 등 리눅스 커맨드라인 유틸리티를 조합하여 정밀한 필터링 쿼리를 빠르게 짜내는 커맨드라인 숙련도가 분석 시간을 대폭 단축시켜 준다는 점을 확인했습니다[cite: 1, 2, 3].
* **팀 내 협업 및 문제 해결 과정**: 문제에 제시된 로그 구조를 함께 다각도로 해석하고, 내부망 통신과 외부 침입 트래픽을 선별해내는 기준을 다듬어가며 팀원들과 함께 지식을 나누고 성장할 수 있었던 소중한 시간이었습니다.

이번 DFC 2026 2차 챌린지를 계기로 클라우드/컨테이너 및 로그 분석 분야에 대한 연구를 더욱 심화하여, 향후 더 복잡하고 고도화된 챌린지에서도 흔들림 없는 분석 역량을 보여줄 수 있도록 준비해 나갈 계획입니다.
